# 21. 実装の進め方（Step 27 以降・実装者向け）

Step 27 以降は、実装を Sonnet、相談役（アドバイザー）を Opus が担当する。方針とタスクは [20](20_canal_town_concept.md) と 22〜26 の仕様書で決めてある。この文書は、どの Step にも共通する決まり。2026-11-12 作成。

## 1. 役割

| 役割 | 担当 | やること |
|---|---|---|
| 実装 | Sonnet | 仕様書どおりに作る。確認して、結果を仕様書の「実装結果」に書く |
| 相談役 | Opus | 仕様の読み方に迷ったとき、2 回試して直らない不具合、作り方の選択で相談を受ける。結果の評価 |
| 方針 | ユーザー | 仕様書に無い判断、仕様を変える判断、見た目・手触りの最終確認 |

- 仕様書に書いていない設計判断が必要になったら、実装を止めてユーザーに質問する（勝手に決めない）
- 値に（仮）と付いたものは、そのまま実装してよい。遊んでから調整する

## 3. 1 つの Step の流れ

1. main から `step<番号>/<内容>` のブランチを切る（エディタを開いたままでよい）
2. 仕様書の該当箇所と、関係する既存の仕様（[04](04_enemy_ai.md)・[11](11_bot_combat.md)・[12](12_macro_ai.md)・[18](18_skills_minimap.md) など）を読む
3. 触る Blueprint の今の中身を、Unreal MCP（EngineWire）で読んでから変える。仕様書の関数名・変数名は調査時点のものなので、実物と違えば実物に合わせ、違いを「実装結果」に書く
4. 小さく作って、その都度コンパイルと PIE で確認する
5. 仕様書の末尾に「実装結果」（仕様との差分、確認できたこと、確認できていないこと）を書く。[TASK.md](TASK.md) のチェックを付ける。`orders/order_YYYYMMDD.md` に指示と結果を 2〜3 行で残す
6. コミットして push する。プルリクエストを作り、競合が無く確認が通っていれば main へ Squash マージしてブランチを消す
7. 「ユーザーが確認する」の項目が残る Step は、マージしてよいが、TASK.md に確認待ちとして残す

## 4. Unreal での決まり

- Blueprint のみ（C++ は使わない）。新しいアセットは `/Game/PARORANT/` 以下
- 関数の引数に Blueprint クラス型を付けない（[07](07_tech_design.md) の注意）。参照は変数で渡す
- 数値は Tuning カテゴリの変数か DataTable に置き、グラフに直書きしない
- 配列のつもりの変数を単体で作らない（[12](12_macro_ai.md) §13 の不具合）。Tick の中のループは必ず上限を付ける
- ログは `[Bot]` `[Director]` `[Chat]` `[Map]` `[Ally]` のように先頭に種類を付ける。確認はログと数値で行い、見た目はスクリーンショットで残す
- 変更したら全 Blueprint をコンパイルし、エラー 0 を確認してから保存する
- エディタが開いている間は、`git switch`・`git stash`・アセットが違うブランチのマージをしない（[18](18_skills_minimap.md) の Git の注意）。作業ブランチ上のコミットと push はよい
- Unreal Editor は 1 つなので、実装のサブエージェントは同時に 1 体だけ動かす

## 5. 確認の決まり

- 「できた」と書く前に、PIE で実際に起こして確かめる。起こせなかったものは「確認できていないこと」に書く
- 難易度は、指定が無ければノーマル（棒立ち）とハード（動く）の両方で見る
- 既存の動き（設置、解除、購入、スキル、ミニマップ、ラウンドの進行）が壊れていないか、1 ラウンド通して確かめる
- 耳で聞く・手触りを見る確認はユーザーに頼む。TASK.md の「実機での確認待ち」に足す

## 6. やらないこと（方針として決定済み）

- ランクの成長（不要）
- 攻守交代（今は取り入れない）
- 特定の VALORANT マップの配置・絵作りをなぞること
- オンライン対戦
